Quick answer: how do you reduce redundancy in requirements?

To reduce redundancy in software requirements that are formalized in Linear Temporal Logic (LTL), compare them by meaning rather than by wording. For each pair of properties, check whether every execution that satisfies one also satisfies the other, that is, whether their languages are included in each other: L(φ′) ⊆ L(φ). If a satisfiable property φ′ implies φ, then every system verified against φ′ also satisfies φ, so φ needs no separate model-checking run. It stays in the requirements document for traceability. Equivalent properties need to be verified only once, unsatisfiable ones must be fixed rather than relied on, and valid ones (tautologies) constrain nothing. The Spot library performs these checks with Büchi automata. This relation is property refinement, formalized for LTL by Brodo, Scalora and Henkler at FSE 2026 [1]. It applies only after natural-language requirements have been formalized, and it does not catch every kind of duplication.

The rest of this tutorial explains each step: which kinds of redundancy exist, the formal definition of refinement, a runnable Spot example, and how pairwise checks become a reduced verification suite.

What is requirements redundancy?

A requirement is redundant when the guarantee it expresses is already provided by other requirements in the same specification. Redundancy is a semantic notion: two requirements can be worded very differently and still say the same thing, or look almost identical and say different things. Distinguishing the following cases avoids most confusion.

Kinds of overlap between formalized requirements, with short LTL examples (Spot syntax)
CaseExampleRedundant?
1. Syntactically identicalG !(door_open & moving) written twiceYes, trivially; a text comparison finds it
2. Logically equivalentG !(door_open & moving) and G (moving -> !door_open)Yes, each implies the other; verify one
3. Related by implicationG (request -> X grant) implies G (request -> F grant)The weaker one is covered by the stronger one
4. Contradictory or unsatisfiableG (request -> grant) & F (request & !grant)No: it is a specification defect that must be fixed
5. Overlapping, not redundantG !(door_open & moving) and G (error -> !moving) share movingNo: neither implies the other
6. Redundant with respect to a setG (error -> !moving) follows from G (error -> alarm) together with G (alarm -> !moving)Yes, but only jointly; no single property implies it

Comparing strings or formula syntax only detects case 1. Cases 2, 3 and 6 require reasoning about all possible executions, because LTL formulas with different syntax can describe the same set of behaviours. Case 4 is the dangerous one: an unsatisfiable formula logically implies every other formula, so a naive implication check would declare it the "strongest" requirement and mark everything else as redundant.

How redundancy accumulates: a realistic scenario

Consider a lift controller developed over several years. The safety team writes "the door is never open while the car is moving". Years later, a legacy specification is merged in that says "whenever the car moves, the door is closed": the same requirement in different words. The control team specifies that each request is granted in the next control cycle, while product management, unaware of this, adds that every request is "eventually" granted. A fairness requirement from a certification checklist adds that repeated requests lead to repeated grants. Each requirement is reasonable on its own, each is formalized as an LTL property, and each becomes a separate model-checking task. Nobody notices that four of them add no assurance. The FSE 2026 paper calls this gradual accumulation of redundant and interdependent properties specification debt [1].

Introducing LTL for requirements verification

Linear Temporal Logic, introduced to computer science by Pnueli [2], describes properties of infinite executions. An execution is seen as a sequence of states, and each state is labelled with the atomic propositions that are true in it. For the lift controller we use six propositions:

  • door_open, moving: the door is open; the car is moving;
  • request, grant: a request arrives; a request is served;
  • error, alarm: a fault is detected; the alarm is on.

Formulas combine propositions with Boolean connectives (¬, ∧, ∨, →; in Spot syntax !, &, |, ->) and temporal operators:

Temporal operators used in this tutorial
OperatorMeaning at the current positionExample and plain-English reading
X φφ holds at the next positionX grant: a grant happens in the next step
F φφ holds now or at some later position ("finally")F grant: a grant happens eventually
G φφ holds now and at every later position ("globally")G !(door_open & moving): the door is never open while moving
φ U ψψ eventually holds, and φ holds at every position before that ("until")!moving U grant: the car stays still until a grant happens

Operators nest. Two common requirement patterns are safety ("something bad never happens") and response ("every trigger is eventually answered"):

G ¬(door_open ∧ moving)Safety: in every state, the door is not open while the car is moving.

G (request → F grant)Response: whenever a request arrives, a grant follows now or later.

GF request → GF grantFairness: if requests arrive infinitely often, grants happen infinitely often.

Traces and languages

Formally, for a set of atomic propositions A, a trace (or word) is an infinite sequence σ = A₀A₁A₂… with each Aᵢ ⊆ A. The language of a formula is the set of traces that satisfy it:

LA(φ) = { σ ∈ (2A)ω | σ ⊨ φ }The set of all infinite executions over the propositions A that satisfy φ.

A system model T (for example a transition system) satisfies φ when every one of its executions does: T ⊨ φ if and only if Traces(T) ⊆ L(φ) [3]. A model checker decides this question, usually by translating ¬φ into a Büchi automaton and searching the product with the model for an accepting cycle [5]. When a suite contains many properties, this is repeated once per property, which is exactly the cost that redundancy inflates.

What is LTL property refinement?

Take φ₁ = G(p ∧ q) ("p and q always hold") and φ₂ = G p ("p always holds"). Every trace that satisfies φ₁ also satisfies φ₂, so L(φ₁) ⊆ L(φ₂). Logical implication between LTL formulas is exactly this language inclusion. Because satisfaction by a model is also an inclusion, it follows directly that

Traces(T) ⊆ L(φ₁) ⊆ L(φ₂) ⟹ if T ⊨ φ₁ then T ⊨ φ₂Verifying the stronger property establishes the weaker one, for any model T over the same propositions.

So for the same system, a successful check of φ₁ already establishes φ₂, and the separate check of φ₂ can be skipped. The argument does not depend on any particular model, which is why the analysis can run before a model exists.

The definition from the FSE 2026 paper

Definition (LTL property refinement; Brodo, Scalora and Henkler [1], Def. 3.1)

Let φ′ and φ be LTL properties, interpreted over the common alphabet A of all atomic propositions occurring in the suite. φ′ refines φ iff

  1. LA(φ′) ⊆ LA(φ), written φ′ ⪯ φ; or
  2. LA(φ′) ⊆ LA(φ) and LA(φ′) ≠ ∅, written φ′ ⪯⁺ φ.

Form (a) is the classical notion. Form (b) adds a non-emptiness condition: the refining property must be satisfiable. Without it, a contradiction such as p ∧ ¬p, whose language is empty, would refine every property, and a "reduced" suite consisting only of false would look sufficient while imposing no meaningful constraint. The paper's reduction method is built on the non-vacuous form ⪯⁺ [1].

The paper also shows that ⪯ is reflexive and transitive (a preorder), and anti-symmetric up to logical equivalence: φ₁ ⪯ φ₂ and φ₂ ⪯ φ₁ hold exactly when φ₁ ≡ φ₂. Modulo equivalence the properties therefore form a lattice, with conjunction as meet and disjunction as join, and refinement is preserved when both sides are conjoined or disjoined with the same property [1]. In practice this means:

  • Equivalence is mutual refinement. A cycle of refinements collapses into one equivalence class, and verifying any one member is enough.
  • Transitivity saves checks. If φ₁ ⪯ φ₂ and φ₂ ⪯ φ₃, then φ₁ ⪯ φ₃ without a separate inclusion test.

Stronger and weaker properties: which one do you verify?

The stronger property is the one with the smaller language: it allows fewer behaviours. Verification effort goes to the stronger property; the weaker one is covered.

Direction of refinement. Arrow: stronger ⪯⁺ weaker
Stronger (verify)Weaker (covered)Why
G(p ∧ q)⪯⁺G pAlways both implies always p.
G p⪯⁺F pIf p holds everywhere, it holds somewhere.
FG a⪯⁺F a"Eventually always a" includes "eventually a" (example from the paper).
G(request → X grant)⪯⁺G(request → F grant)A grant in the next step is in particular a grant eventually.
G ¬(door_open ∧ moving)≡G(moving → ¬door_open)Same language: refinement holds in both directions, so verify one.

The converse never follows: knowing that G p holds tells you nothing about G(p ∧ q). Reversing the direction is the most common error in practice, see common mistakes.

Detect redundant LTL requirements using Spot

Spot is a C++ library with Python bindings for LTL and ω-automata [7]. It translates LTL formulas into Büchi automata and offers language inclusion and equivalence checks, which is all that semantic redundancy detection needs. Spot can be installed, for example, from conda-forge (conda install -c conda-forge spot) or from the Debian and Fedora packages listed in its installation guide [10].

From pairwise implication to property-set reduction

Pairwise checks become useful when their results are combined into a decision for the whole suite: which properties must still be model-checked, and which are guaranteed by the ones that are. Here is the running suite with its plain-English meaning.

IDLTL (Spot syntax)Plain English
R1G !(door_open & moving)The door is never open while the car is moving.
R2G (moving -> !door_open)Whenever the car moves, the door is closed.
R3G (request -> X grant)Every request is granted in the next step.
R4G (request -> F grant)Every request is eventually granted.
R5GF request -> GF grantIf requests keep arriving, grants keep happening.

Pairwise refinement reduces ten model-checking tasks to five (R1, R3, R8, R9, R10) and flags one defective requirement. The additional joint-entailment step brings it to four. Why the four retained checks suffice for this example: for any model T, if T satisfies R1, R3, R8 and R9, then

  • Traces(T) ⊆ L(R1) = L(R2), so R2 holds;
  • Traces(T) ⊆ L(R3) ⊆ L(R4) ⊆ L(R5), so R4 and R5 hold;
  • Traces(T) ⊆ L(R8) ∩ L(R9) ⊆ L(R10), because at every position an error implies the alarm and the alarm implies a stopped car;
  • R7 holds on every trace anyway.

R6 cannot be established for any model with at least one execution, so it is reported for correction rather than "covered". The requirements R2, R4, R5, R7 and R10 stay in the specification; only their separate verification runs are skipped.

How the FSE 2026 paper operationalizes refinement

The script above shows the idea. The paper turns it into a two-stage methodology inserted between requirement formalization and verification [1]:

  1. Partitioning and filtering (Algorithm 1). For each property, a Büchi automaton is constructed. Properties whose language is empty (contradictions) or universal (tautologies) are removed. The remaining properties are partitioned into classes of properties connected by shared atomic propositions, using a Union-Find structure. The paper shows that this loses no refinement: if φ′ ⪯⁺ φ and φ is not valid, the two share at least one atomic proposition.
  2. Refinement analysis per class (Algorithm 2). Within each class, language inclusion is checked for pairs of properties and recorded as edges of a refinement graph, with transitivity used to expand known relations instead of re-checking them. The most refined properties are the source nodes of the graph; cycles, which by anti-symmetry consist of equivalent properties, contribute one arbitrarily chosen representative.
  3. Minimal sufficient subset. The union of the source nodes of all classes, Φ′, is the set that is verified. The paper proves that it is sufficient (its satisfaction guarantees the whole suite) and minimal in the sense that no selected property is refined by another selected property. All original properties are kept for documentation, traceability and certification; Φ′ is used only to optimize verification.

The tutorial script mirrors steps 1–3 in a naive way: it checks every ordered pair without exploiting transitivity, uses no further automata optimizations, and is only meant for small suites. The paper's prototype relies on Spot for LTL-to-Büchi translation, automata simplification and inclusion checking, and the authors stress that the approach is tool-agnostic.

Pairwise refinement versus joint entailment

Refinement compares one property with one property. Some redundancy only appears when several properties are combined, as with R10. Detecting it requires checking whether a conjunction of other properties implies a candidate, and there are exponentially many subsets to consider. Barnat et al. follow this subset-based route for avionics requirements and report that it becomes very expensive even for small suites [13]; the FSE 2026 paper discusses this trade-off and deliberately builds on pairwise refinement, which scales quadratically in the number of properties (plus the cost of the automata) [1].

The optional step in the script is a cheap compromise for small suites: it tries to drop each retained property if the conjunction of the others implies it. This is sound, because every dropped property is implied by properties that remain implied by the final set, but the result depends on the order of the properties and is not guaranteed to be the smallest possible set. It should not be described as optimal.

Why not just simplify LTL formulas?

Several established techniques reduce verification cost or improve specification quality. They act on different objects and answer different questions.

Comparison of techniques related to redundant requirements and verification cost
TechniqueWhat it changesProblem it solvesWhat it does not do
Syntactic duplicate detectionNothing; compares text or syntax treesFinds identical or near-identical requirements, also in natural language [16]Recognize equivalent or implied formulas with different syntax
LTL formula simplificationOne formula, rewritten into an equivalent, simpler one [11], [7]Smaller automata and faster checks for that formulaReason about the relation between separate requirements
Equivalence checkingNothing; pairwise L(φ) = L(ψ)Finds semantic duplicatesDetect strictly stronger or weaker properties
Pairwise implication / subsumptionNothing; pairwise L(φ) ⊆ L(ψ)Finds properties implied by others [14], [13]On its own, exclude vacuous implication by unsatisfiable formulas
Property refinement and suite reductionThe set of properties that is model-checkedFewer independent verification tasks, model-independent, with non-vacuous refinement [1]Change the model, or capture all joint entailments
Vacuity detectionNothing; analyses one property, typically against a modelFinds sub-formulas that do not matter for satisfaction [12]Compare different properties of a suite
Model abstraction, state-space reductionThe model or its explorationFewer states to explore per check [3], [4]Reduce the number of properties
Multi-property model checkingHow several checks share workReuses information across the checks of many properties [15]Decide that a property needs no check at all

The key distinction: property-set reduction targets the number of independently verified specifications, while state-space reduction targets the model or its exploration. The two are orthogonal and can be combined. The FSE 2026 implementation itself uses Spot's formula and automata simplifications as a preprocessing step [1].

Read the research paper Abstract, PDF and BibTeX

This tutorial is an introduction to the ideas of the paper above, presented at the ACM International Conference on the Foundations of Software Engineering (FSE 2026) and published in Proceedings of the ACM on Software Engineering. The paper makes three contributions [1]:

  • Formal semantics. A language-inclusion definition of property refinement for LTL with a non-emptiness condition, and its algebraic properties: preorder, anti-symmetry modulo equivalence, lattice structure, and composability with conjunction and disjunction.
  • Specification partitioning and refinement analysis. An algorithm that filters contradictions and tautologies, partitions the suite by shared atomic propositions, and builds a refinement graph within each class, with a complexity analysis.
  • Minimal sufficient subset. A formal problem statement and the proof that the selected most-refined properties are sufficient and minimal with respect to refinement, together with an empirical evaluation.

Reported experimental results

The evaluation uses 141 benchmarks derived from the BEEM collection [17]: mutual exclusion protocols (45), communication protocols (27), distributed algorithms (20), scheduling and resource allocation (24) and general model-checking examples (25). Suites range from a handful of properties to more than 600 distinct formulas. Each benchmark is model-checked twice with the Spot–LTSmin–DVE backend, once with the original suite and once with the reduced one, with identical models and settings. As reported in the paper (Table 1):

  • the number of required verification tasks fell in 109 of 141 benchmarks (77.3%), by up to 75%, with a mean of about 36% and a median of 50%;
  • model checking of the reduced suite was 1.63× faster on average (median 1.75×, best 4.2×);
  • including the cost of the refinement analysis, 137 of 141 benchmarks (97%) had a net benefit within a 3% measurement tolerance; across all benchmarks, about 20.6 hours of model checking were saved for about 12 minutes of analysis;
  • the refinement overhead had a median of 0.035% of the baseline verification time, a mean of 2.22% and a worst case of 54.5%.

These are results on the evaluated benchmarks, not general performance guarantees. The benefit depends on how much redundancy a suite contains (the paper reports a correlation between reduction and net gain) and on how expensive each model-checking run is. Because the analysis is done once on the specification while verification is repeated for every model revision, its cost is amortized over a development lifecycle.

Limitations and trade-offs

  • Automata construction. LTL satisfiability and inclusion are PSPACE-complete [6], and translating a formula into a Büchi automaton is exponential in the formula size in the worst case. The paper names caching, parallelization and sound syntactic implication rules as mitigations and leaves more sophisticated heuristics to future work.
  • When it does not pay off. In the 4 benchmarks with a net loss, large and complex property suites were combined with comparatively small models, so the one-time analysis could not be amortized by cheaper verification.
  • Partitioning. Most evaluated benchmarks were monolithic and produced only one to three classes; the authors expect partitioning to matter more for industrial systems with distinct components.
  • Model independence. Refinement holds over all traces. Relations that hold only under a specific model's constraints are not detected, which is the price of an analysis that remains valid when the model changes.

Common mistakes and limitations

Reversing the implication direction

The stronger property (smaller language) is verified and the weaker one is covered, never the reverse. With Spot, spot.contains(a, b) asks whether L(b) ⊆ L(a), i.e. whether b implies a. Test both directions on a known pair such as G p and F p before trusting a pipeline.

Treating unsatisfiable properties as the strongest specification

An unsatisfiable property implies everything, so it must be filtered out before refinement analysis. This is the purpose of the non-emptiness condition in ⪯⁺. An unsatisfiable requirement is a defect to report, not a property that covers others.

Confusing semantic redundancy with textual similarity

G (request -> X grant) and G (request -> F grant) look alike and are related, but they are not equivalent; G !(door_open & moving) and G (moving -> !door_open) look different and are equivalent. Only a semantic check decides.

Mixing incompatible system assumptions

Refinement is only meaningful between properties that refer to the same system and the same interpretation of the atomic propositions. If grant means "request accepted" in one document and "door opened for a passenger" in another, a formal implication between the formulas says nothing about the requirements. Harmonize the vocabulary first. Likewise, properties written under different environment assumptions, or for different model variants, must not be mixed in one analysis.

Confusing model-independent implication with implication under model constraints

Refinement as described here holds for all traces. Under a particular model, more properties may turn out to be related (for instance because the model never issues two requests in a row), but such relations must be established with the model and become invalid when the model changes. Model-dependent approaches such as D³ address this setting with additional model-checking runs [14].

Removing requirements instead of skipping their checks

A covered property is not deleted. It still documents an intention, links to its source requirement, may be needed for certification evidence, and becomes relevant again if the stronger property is later weakened or removed. Keep it in the specification, record which retained property covers it, and re-run the analysis whenever the suite changes. Reviewing the redundancy itself is often valuable: it can reveal duplicated elicitation or an accidental strengthening by one team.

Confusing pairwise implication with joint entailment

A pairwise analysis keeps a property that is implied only by a combination of others (R10 in the example). Claiming that a pairwise result is the smallest possible sufficient set is therefore wrong in general. Joint entailment can be checked for small suites, at a higher cost.

Ignoring the cost of automata construction

Most practical formulas translate quickly, but some produce very large automata. Measure the analysis time, set time limits for individual checks, cache automata (as language_containment_checker does), and treat a timed-out check as "unknown", which means the property is kept.

Frequently asked questions

How can I detect redundant software requirements automatically?

For textual duplicates, clone and similarity detection on the requirement documents works. For semantic redundancy, formalize the requirements, for example in LTL, then check satisfiability and pairwise language inclusion with a tool such as Spot. A property implied by a satisfiable, retained property is redundant for verification. See the Spot example.

How can I reduce the number of LTL properties in model checking?

Remove unsatisfiable properties (and fix them), skip valid ones, verify one representative per equivalence class, and skip every property refined by a retained satisfiable property. This is the reduction to a minimal sufficient subset described in property-set reduction and in the FSE 2026 paper [1].

How do I know whether two LTL formulas are equivalent?

Two formulas are equivalent when they have the same language, i.e. each implies the other. In Spot, spot.are_equivalent(f, g) checks this directly; ltlfilt --equivalent-to does the same on the command line.

Can Spot check whether one LTL formula implies another?

Yes. spot.contains(weaker, stronger) returns True if stronger implies weaker, because it tests whether the language of its second argument is included in that of its first. For many checks, spot.language_containment_checker() caches automata. See checking implication with Spot.

What is a minimal sufficient set of LTL properties?

A subset Φ′ of a suite Φ is sufficient if every system satisfying all properties in Φ′ satisfies all properties in Φ, and minimal if no property can be removed without losing sufficiency [1]. The FSE 2026 method computes such a set from the most refined properties of each class, with minimality relative to the refinement relation; redundancy that only arises jointly is a separate question (see joint entailment).

What is the difference between LTL simplification and property refinement?

Simplification rewrites one formula into an equivalent, simpler formula. Refinement compares different formulas and decides which ones need to be verified at all. They are complementary; see the comparison.

Does reducing redundant properties preserve verification guarantees?

Yes, for refinements that are actually established: if φ′ ⪯⁺ φ and the model satisfies φ′, it satisfies φ, because Traces(T) ⊆ L(φ′) ⊆ L(φ). The guarantee depends on correct formalization, a consistent vocabulary, and on treating unknown or timed-out checks conservatively.

Can this approach work with natural-language requirements?

Not directly. Semantic refinement needs formal properties. Natural-language requirements first have to be formalized, manually or with specification patterns and tool support, and the formalization should be reviewed. Once formalized, the analysis can also be traced back to the original requirements to explain where redundancy comes from.

Summary: what you learned

  • Requirements redundancy is semantic: equivalence, implication and joint entailment cannot be found by comparing text.
  • For LTL, implication is language inclusion, L(φ′) ⊆ L(φ), and verifying the stronger property establishes the weaker one for any model.
  • Property refinement adds non-emptiness, L(φ′) ≠ ∅, so unsatisfiable formulas cannot vacuously cover others.
  • With Spot, spot.contains(weaker, stronger) tests implication, spot.are_equivalent tests equivalence, and spot.translate(f).is_empty() tests unsatisfiability.
  • Combining pairwise refinements yields a reduced verification suite; covered requirements stay in the specification.
  • The FSE 2026 paper formalizes this as the minimal sufficient subset problem and reports up to 75% fewer verification tasks on 141 benchmarks [1].
