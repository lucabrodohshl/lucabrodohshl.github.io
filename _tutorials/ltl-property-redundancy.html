When can a requirement check be omitted?

If a system satisfies an LTL property, it also satisfies every property that follows from it. For example, “every request is granted in the next step” implies “every request is eventually granted.” Once the stronger requirement has been verified, the weaker one needs no separate model-checking run.

To find these relations, check satisfiability and consistency, then compare the properties' languages with Spot. Equivalent properties need only one representative; weaker properties are covered by retained stronger ones. Keep the original requirements and record these dependencies for traceability.

This is the basis of LTL property refinement, developed in the FSE 2026 paper by Brodo, Scalora and Henkler [1]. It applies to formalized requirements. Natural-language requirements need a reviewed formalization before this analysis can establish anything about them.

What counts as redundancy?

A requirement is redundant with respect to a set when the other requirements already entail it. This can happen even when their wording and formula syntax differ.

Consider a lift controller maintained by several teams. One team requires that the door remain closed while the lift moves. A legacy specification states the same rule in different words. Elsewhere, a response deadline of one control cycle already covers a more general promise of eventual service. Each requirement has a reason to appear in the documentation, but they need not all be checked independently. The paper describes the accumulation of redundant and interdependent properties as specification debt [1].

LTL for requirements

Linear Temporal Logic describes properties of infinite executions [2]. At each step, atomic propositions describe what is true. Our controller uses door_open and moving for its physical state, request and grant for service events, and error and alarm for fault handling.

LTL combines these propositions with Boolean connectives and temporal operators. Spot writes negation, conjunction, disjunction and implication as !, &, | and ->.

The four temporal operators used here
OperatorMeaningExample
X φφ holds at the next step.X grant: a grant occurs in the next step.
F φφ holds now or at some later step.F grant: a grant eventually occurs.
G φφ holds now and at every later step.G !moving: the lift never moves.
φ U ψψ eventually holds; φ holds at every earlier step.!moving U grant: the lift remains still until a grant occurs. A grant must occur.

Operators can be nested to express safety, response and fairness requirements:

G ¬(door_open ∧ moving)The door is never open while the lift is moving.

G (request → F grant)At every step with a request, a grant occurs at that step or later.

GF request → GF grantIf requests occur infinitely often, grants also occur infinitely often.

These formulas use a deliberately small event model. They do not distinguish passengers or match individual requests to individual grants. A specification that needs those distinctions must represent them explicitly.

Traces and languages

For a set of propositions A, a trace is an infinite sequence σ = A₀A₁A₂…, where Aᵢ ⊆ A lists the propositions true at step i. A formula's language is the set of traces that satisfy it:

LA(φ) = { σ ∈ (2A)ω | σ ⊨ φ }All infinite executions over A that satisfy φ.

A system model T satisfies φ when all its traces belong to this language: Traces(T) ⊆ L(φ) [3]. An automata-based model checker typically translates ¬φ into a Büchi automaton and looks for a system execution accepted by that automaton [5]. Such an execution is a counterexample to φ.

What is LTL property refinement?

Let φ₁ = G(p ∧ q), meaning that p and q always hold, and φ₂ = G p, meaning that p always holds. Every trace satisfying φ₁ also satisfies φ₂:

L(φ₁) ⊆ L(φ₂)φ₁ implies φ₂. The stronger property has the smaller language.

If every execution of a model satisfies φ₁, each also satisfies φ₂. A successful verification of φ₁ therefore establishes φ₂ for the same model. If the check of φ₁ fails, that result alone does not tell us whether φ₂ holds.

The non-emptiness condition

LTL property refinement [1, Definition 3.1]

Interpret both properties over the same alphabet A, containing all propositions used in the suite. The paper distinguishes:

  • φ′ ⪯ φ when LA(φ′) ⊆ LA(φ): every trace satisfying φ′ satisfies φ.
  • φ′ ⪯⁺ φ when that inclusion holds and LA(φ′) ≠ ∅: φ′ must also be satisfiable.

The second relation excludes vacuous refinement by contradictions. An unsatisfiable formula has an empty language and therefore implies everything, but no system with at least one execution can satisfy it. It cannot serve as evidence that the requirements have been met.

Equivalence is implication in both directions. Equivalent properties can be grouped, with one representative selected for verification. Refinement is also transitive: if one property implies a second and the second implies a third, no additional inclusion check is needed to infer the first-to-third relation.

The converse does not follow in these examples. Eventual service, for instance, permits a delay of several steps and cannot establish next-step service.

Checking implication with Spot

The method in the FSE 2026 paper

The paper places refinement analysis between formalization and model checking [1]:

  1. Filter and partition. Construct automata, identify contradictions and tautologies, and group the remaining properties by connections through shared atomic propositions. These groups restrict which properties need comparison. They are distinct from groups of logically equivalent formulas.
  2. Build refinement relations. Check language inclusion within each group and record the relations in a graph. Use transitivity to infer further relations. Mutual refinement identifies equivalent formulas.
  3. Select representatives. Keep the most refined properties, choosing one representative from each selected equivalence class. In a graph oriented from stronger to weaker, these are the source components.

The shared-proposition partition is justified after filtering: if a satisfiable property implies a non-tautological property, the two must share at least one atomic proposition. The tutorial script uses this test to skip disjoint pairs, but compares the remaining ordered pairs directly rather than implementing the paper's full graph analysis.

What pairwise analysis can miss

The paper calls the selected set a minimal sufficient subset. For the pairwise construction, the practical guarantee is that every remaining candidate is implied by a selected property, and no selected representative is strictly refined by another selected representative. This does not by itself rule out redundancy caused by a conjunction.

R10 illustrates the distinction: neither R8 nor R9 implies it alone. A pairwise result can therefore contain a property that is redundant with respect to the rest of the set. Inclusion-minimality under arbitrary joint entailment and minimum cardinality are stronger requirements.

The script's optional final pass checks each property against the conjunction of the others. It performs one pass in a fixed order and does not guarantee a set of minimum cardinality. Although the number of checks is small, the conjunctions can make automata construction expensive. Exhaustively exploring combinations adds a separate combinatorial cost; see the discussion of subset-based analysis in the paper and Barnat et al. [1], [13].

Why not just simplify the formulas?

Simplification can make a formula easier to verify. Suite reduction asks which requirements need independent checks. Both can help, and they can be used together.

Reported results

The evaluation uses 141 benchmarks derived from BEEM [17], covering mutual exclusion, communication protocols, distributed algorithms, scheduling and other model-checking examples. Each model is checked with its original and reduced property suites using the Spot–LTSmin–DVE backend. Table 1 reports:

  • Fewer tasks in 109 of 141 benchmarks. The reduction reaches 75%, with a mean of 35.95% and a median of 50%.
  • A mean model-checking speedup of 1.63×. The median is 1.75× and the best case in Table 1c is 4.2×.
  • About 20.6 hours of gross verification time saved across the benchmarks, against roughly 12 minutes of refinement analysis.
  • A median analysis overhead of 0.035% of baseline verification time. The mean is 2.22% and the worst case is 54.5%.

These figures describe the evaluated benchmarks and use the speedup metric reported in Table 1c. They are not performance guarantees for other models or property suites.

Costs and applicability

The benefit depends on the suite's redundancy and the cost of the checks avoided. Four benchmarks had a net loss: analysis of their property suites cost more than the verification time it saved. The same analysis can be reused when the model changes, provided the properties and their semantics remain unchanged.

LTL satisfiability and inclusion are PSPACE-complete [6], and the constructed automata can be exponential in the formula size. Caching and partitioning reduce repeated work but do not remove this worst-case cost. Most evaluated suites produced only one to three proposition-connected groups, so the evaluation gives limited evidence about partitioning benefits for more modular specifications.

Assumptions and limitations

Check the implication direction

Verify the stronger property and use it to establish the weaker one. Spot's argument order is easy to reverse: spot.contains(a, b) tests whether b implies a. A small known example, such as always p implying eventually p, helps catch this error.

Check consistency as well as individual satisfiability

A contradiction must be reported and corrected. Also check whether individually satisfiable requirements can hold together: G p (“p always holds”) and F !p (“p is eventually false”) are each satisfiable but jointly inconsistent. Their conjunction implies everything vacuously. The example stops if the non-rejected requirements are jointly inconsistent.

Separate similarity from implication

Changing X to F can weaken a response requirement while leaving its text almost unchanged. Conversely, a Boolean rewrite can change the syntax without changing the meaning. Textual similarity can guide review, but it does not establish either equivalence or refinement.

Use a common interpretation

Proposition names must have the same meaning throughout the suite. If grant means “request accepted” in one source and “passenger served” in another, an implication between the formulas does not establish the intended requirement relation. Align the vocabulary, time-step interpretation, model variants and environment assumptions first.

Distinguish universal from model-dependent implication

The checks here range over all traces. Further implications may hold only under a model's constraints or explicit environment assumptions. Record those dependencies: such relations need to be reconsidered when the constraints change. D³ is related work on exploiting dependencies for model checking [14].

Keep the requirements and their coverage records

An implied requirement can still be useful for documentation, certification or communication with its owners. Record which retained properties cover it. Recompute the affected relations when a property changes, and report an omitted check as established only after its covering checks succeed. If a stronger check fails, a weaker requirement may still hold and may need a separate diagnostic check.

State what kind of reduction was computed

A pairwise reduction does not establish that no property follows from a combination of others. Likewise, an inclusion-minimal set need not have the fewest possible members. State the criterion used and avoid describing an arbitrary reduced set as globally optimal.

Handle expensive checks conservatively

Cache automata and measure preprocessing time. In a production workflow, use time limits and retain properties when an inclusion check is inconclusive. A timeout provides no proof of redundancy.

Frequently asked questions

Can redundant requirements be detected automatically?

Once requirements are formalized, tools can check their satisfiability, equivalence and implication. These checks identify semantic redundancy in the formulas. They do not establish that the formalization captures the original intent; that still needs review.

How can I reduce the number of LTL model-checking tasks?

Report contradictions, set aside tautologies, choose one representative for equivalent properties, and retain the strongest properties needed to cover the others. The worked reduction shows where a further joint-entailment check can help.

How do I check whether two LTL formulas are equivalent?

Use spot.are_equivalent(f, g), or ltlfilt --equivalent-to on the command line. Equivalence means both formulas accept exactly the same traces.

Can Spot check whether one formula implies another?

Yes: spot.contains(weaker, stronger) checks whether every trace satisfying stronger satisfies weaker. See the first Python example for both directions.

What is a minimal sufficient set of LTL properties?

A sufficient subset entails the full suite. It is inclusion-minimal if removing any member loses that sufficiency; it has minimum cardinality if no smaller sufficient subset exists. A pairwise refinement analysis establishes coverage by individual properties, so its minimality claim needs that qualification. See the distinction using R10.

How does refinement differ from LTL simplification?

Simplification rewrites a formula while preserving its meaning. Refinement compares the strength of separate formulas. The resulting relations can be used to select a smaller verification suite while preserving the original requirement IDs.

Does omitting redundant checks preserve the guarantees?

Yes, when the retained properties entail the omitted ones and the retained checks succeed for the same model and assumptions. A failed or inconclusive retained check does not establish its dependants.

Can this be applied directly to natural-language requirements?

No. The requirements must first be formalized. Textual duplicate detection can assist earlier review, but semantic LTL analysis concerns the resulting formulas and their chosen interpretation.

Using the reduced suite

For this example, verify R1, R3, R8 and R9, then record the implied requirements as covered if those checks pass. Keep R6 open as a specification defect. After it is corrected, rerun the analysis before treating the complete suite as verified.

For another suite, follow the same sequence: review the formalization, check consistency, establish implication relations, and keep a record of why each omitted check is covered. The useful output is a smaller verification suite together with an explanation of its coverage.
